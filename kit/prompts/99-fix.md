Используйте, когда что-то не так и нужно точечно починить. Скопируйте промт,
выберите подходящий сценарий ниже, подставьте свои детали в < … > и отправьте
агенту.

---

```
Режим: фикс. Действуй по kit/playbook/08-iteration.md.

Главное правило: любое изменение делается в ОДНОМ конфиге (metric-catalog,
ui-layout, brand.config, source-manifest), а не в коде. Если я прошу «поправь
в коде» — перепроверь, не должна ли правка быть в конфиге, и предложи альтернативу.

Сценарий:

<выбери и впиши один из шаблонов ниже>
```

## Шаблон A — «KPI показывает не то число»

```
Проблема: KPI <id> в дашборде показывает <X>, ожидалось <Y>.
Источник проверки: <укажи, где именно я считал Y вручную>.

Действия:
1. Открой metric-catalog.yaml и проверь formula для <id>.
2. Открой source-manifest.yaml и проверь mapping/transforms для задействованных
   датасетов.
3. Пересчитай вручную по данным из data/dashboard.json и сообщи, совпадает ли
   с моим Y.
4. Если расхождение в формуле — исправь её в каталоге и перегенерируй
   dashboard.json скриптом нормализации.
5. Если расхождение в данных — исправь mapping/transforms и пересобери.
6. Покажи, что изменилось, и новое значение KPI.
```

## Шаблон D — «Фильтр не применяется»

```
Проблема: фильтр <id> не влияет на данные (KPI/графики/таблицы).

Действия:
1. Проверь ui-layout.yaml -> filters[<id>]: есть ли он и корректны ли
   options / options_from.
2. Проверь, что поле фильтра есть в соответствующих датасетах в dashboard.json.
3. В коде UI проверь, что применение фильтра идёт через единую функцию
   applyFilters(), а не дублируется.
4. Если фильтр требует пересборки dashboard.json (напр. разные периоды
   агрегируются на этапе сборки) — перегенерируй JSON на нужных срезах.
5. Покажи, что фильтр теперь работает.
```

```

Действия:

   содержит реальные значения.
```

## Шаблон H — «Рассинхрон ui-layout.yaml ↔ dashboard.json»

```
Проблема: в ui-layout.yaml есть bind на charts.<id> / tables.<id> / kind: image,
которого нет (или он пустой) в dashboard.json. Либо в dashboard.json есть
series с forecastable: true, но парного ряда *_forecast нет / его формат
неправильный.

Действия:
1. Открой ui-layout.yaml и собери список всех bind: charts.* / tables.* и
   всех kind: image.
2. Сверь с data/dashboard.json. Для каждого несовпадения пометь, где
   чинить:
   - нет ключа в dashboard.json -> чинить сборку (data-mapper,
     20-map-data.md);
   - bind в ui-layout.yaml ссылается на несуществующий id -> чинить
     ui-layout.yaml;
   - для forecastable: true нет *_forecast или он не в формате
     { month, actual, forecast, lower, upper } -> чинить скрипт
     нормализации.
3. Исправь минимально необходимый конфиг / скрипт, перегенерируй
   dashboard.json. НЕ дописывай данные прямо в dashboard.json руками —
   только через конфиги и скрипт.
4. Подними meta.version и обнови meta.generated_at.
5. Прогони пункты §11 из kit/templates/acceptance-checklist.md.
6. Покажи список изменений (какие ключи появились/ушли) и подтверди,
   что все bind теперь разрешаются.
```

## Шаблон I — «Битые картинки / несуществующие пути»

```
Проблема: на дашборде не грузится картинка (<какая: логотип / износ /
другая>). В консоли 404 или пустой <img>.

Действия:
1. Проверь, по какому пути UI пытается загрузить картинку (DevTools ->
   Network).
2. Проверь, где файл физически лежит (assets/... или data/assets/... и т.п.).
3. Выбери КАНОНИЧНЫЙ путь (обычно assets/... из корня статической
   раздачи) и приведи к нему:
   - если файл лежит не там — перенеси / добавь раздачу;
   - если путь в данных/конфиге другой — поправь там, где данные
     генерируются (source-manifest.yaml / скрипт нормализации /
     brand.config.yaml).
4. Убедись, что в UI включён fallback путей (assets/... ↔ data/assets/...),
   как описано в kit/skills/dashboard-builder/SKILL.md §9.
5. Перезапусти и проверь, что img.naturalWidth > 0.
6. Закрой пункт §11 чек-листа «изображение загружено».
```

## Шаблон J — «Фильтр обнуляет всю вкладку»

```
Проблема: при выборе значения фильтра (например, конкретного объекта /
класса / периода) вся вкладка становится пустой, хотя часть данных должна
остаться.

Действия:
1. Найди функцию применения фильтра в UI.
2. Проверь, что фильтр применяется ТОЛЬКО к тем датасетам/графикам, у
   которых реально есть соответствующее поле (или выбранное значение в
   нём встречается). См. правило 5.3 в kit/prompts/30-build-ui.md и §8 в
   kit/skills/dashboard-builder/SKILL.md.
3. Для несовместимых блоков — оставляй общий срез, не обнуляй.
4. Повтори проверку на связке «период + объект + класс», чтобы
   комбинации не давали полностью пустую вкладку.
5. Закрой пункт §11 «смена фильтра не обнуляет вкладку».
```

## Шаблон L — «Windows: execution policy / занятый порт / кракозябры»

```
Проблема (нужное подчеркнуть):
- PowerShell ругается на execution policy при запуске .ps1;
- порт 5173 / 8787 занят и сервер не стартует;
- кириллица в консоли / логах отображается как кракозябры;
- после правок в коде «ничего не меняется», старый процесс висит.

Действия:
1. Execution policy:
   - Для текущей сессии: `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`.
   - Для пользователя: `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`.
   - Либо использовать .cmd-обёртку, а не прямой запуск .ps1.
2. Занятый порт:
   - `netstat -ano | Select-String ":<port> "`;
   - `Stop-Process -Id <PID> -Force`;
   - или `npx kill-port <port>`;
   - добавить в скрипт старта шаг «освободить порт перед запуском».
3. Кракозябры в логах:
   - `chcp 65001`;
   - `$OutputEncoding = [Text.UTF8Encoding]::new()`;
   - `[Console]::OutputEncoding = [Text.UTF8Encoding]::new()`;
   - вписать это в .ps1-обёртку запуска дашборда.
4. Висящие процессы node/py:
   - `Get-Process node, py, python -ErrorAction SilentlyContinue | Stop-Process -Force`;
   - после этого перезапустить.
5. Обнови kit/faq.md §21–§25, если нашёл новый Windows-edge case, не
   описанный там.
```

## Шаблон M — «LLM нестабильно выбирает build_chart (нет артефактов)»

```
Проблема: на вопросы «покажи топ-N … графиком» агент иногда отдаёт только
текст без artifacts, trace.toolsUsed не содержит build_chart.

Действия:
1. Включить/починить детерминированный intent-router из
   kit/skills/agent-tools/SKILL.md -> «Детерминированный intent-router».
2. Пре-процессор на сервере перед вызовом LLM:
   - детектит маркеры «топ N», «график», «таблица»;
   - выставляет visualize_required = true, top_n = N;
   - подкладывает эти значения в системный промт.
3. Пост-процессор после финала LLM:
   - если visualize_required = true и в ответе нет artifacts — делает
     один retry с принудительной подсказкой «верни tool_calls с
     build_chart/build_table»;
   - если всё равно нет — использует локальный fallback (query_data +
     build_chart напрямую со стороны сервера).
4. Smoke: 10 раз подряд POST /api/agent с «Покажи топ-5 … графиком» —
   во всех 10 ответах должны быть artifacts и trace.toolsUsed содержать
   build_chart. Любой провал = FAIL, не считать фикс завершённым.
```

## Шаблон N — «Кириллица / кодировки при сборке dashboard.json»

```
Проблема: в dashboard.json / UI / логах вместо кириллицы кракозябры, или
mapper не находит колонку Excel с кириллическим именем.

Действия:
1. Проверь процесс чтения источника по kit/skills/data-mapper/SKILL.md
   (раздел про кодировки):
   - csv/tsv: автодетект в порядке utf-8-sig, utf-8, cp1251, cp866,
     windows-1252;
   - xlsx/xls — только через openpyxl/pandas/xlsx, без ручного codec;
   - БД — client_encoding = UTF8 / SET NAMES utf8mb4.
2. В скрипте сборки dashboard.json явно задать:
   - Python: `open(..., encoding="utf-8")`, `json.dump(..., ensure_ascii=False)`;
   - Node: `fs.writeFileSync(path, JSON.stringify(data), "utf8")`.
3. В source-manifest.yaml: mapping.columns должен совпадать с именем
   колонки посимвольно (регистр, пробелы). Не транслитерировать.
4. PowerShell-консоль: `chcp 65001` и `$OutputEncoding =
   [Text.UTF8Encoding]::new()` в обёртке запуска билда.
5. Повторить сборку и проверить: кириллица в dashboard.json читается как
   есть (не как "\u0426\u0435\u0445" без опций ensure_ascii: false).
```

## Шаблон O — «Фильтр скрывает датасеты без нужного поля»

```
Проблема: при выборе, например, объекта/сегмента часть виджетов на вкладке
пропадает, потому что у их датасета нет поля фильтра или выбранного значения.

Действия:
1. В UI построить мапу compatibility: для каждого фильтра — список
   датасетов/графиков, у которых реально есть соответствующее поле и у
   которых в данных встречается выбранное значение.
2. Правило применения:
   - если датасет совместим по полю и значению — фильтруем;
   - если датасет не содержит поле или значение отсутствует — НЕ трогаем,
     оставляем общий срез;
   - отдельно помечаем такие виджеты дискретным бейджем «не затронут
     фильтром <id>», чтобы пользователь понимал, почему значение не
     сменилось.
3. Проверить, что при любой комбинации фильтров вкладка не становится
   полностью пустой (если хотя бы один виджет несовместим — он остаётся
   на общем срезе).
4. Закрыть пункт §11 чек-листа «смена фильтра не обнуляет вкладку».
```

## Шаблон K — «Правки dashboard.json не видно в UI (кэш)»

```
Проблема: dashboard.json на диске обновлён, но UI показывает старые
значения. Помогает только жёсткая перезагрузка / очистка кэша.

Действия:
1. Проверь, что UI грузит dashboard.json с cache: "no-store" (или
   эквивалентом для стека). Если нет — исправь.
2. Проверь, что в meta.generated_at стоит свежая дата, а meta.version
   увеличивается при каждом релевантном изменении.
3. Проверь заголовки статического сервера: для dashboard.json не должно
   быть долгого Cache-Control / immutable.
4. Если используется Service Worker — добавь инвалидатор по
   meta.version или отключи кэш для dashboard.json.
5. Закрой пункт §11 «dashboard.json грузится без кэша».
```

## Шаблон G — «Пересборка по расписанию»

```
Задача: автоматически пересобирать dashboard.json каждые <часы/день>.

Действия:
1. Определи раннер: cron (Linux) / Task Scheduler (Windows) / GitHub Actions
   / CI пайплайн.
2. Создай команду build:dashboard, которая прогоняет скрипт нормализации и
   валидацию по dashboard.schema.json.
3. Добавь уведомление при сбое (лог или письмо) — секреты через переменные
   окружения.
4. Не коммить обновлённый dashboard.json автоматически, если данные
   чувствительные. Публикуй в защищённое хранилище.
```
