# 20 — Сборка dashboard.json из источников

Отправьте, когда готовы `source-manifest.yaml` и `metric-catalog.yaml` в корне
проекта.

---

```
Режим: data-mapper. Действуй по kit/skills/data-mapper/SKILL.md и
kit/playbook/03-source-mapping.md.

Цель: собрать dashboard.json, валидный по kit/templates/dashboard.schema.json.

Шаги:

1. Прочитай source-manifest.yaml и metric-catalog.yaml из корня моего проекта.
   Если чего-то не хватает — останови работу и задай конкретные вопросы.

2. Проверь манифест:
   - все kind поддерживаются;
   - все mapping.to перечислены в canonical_datasets;
   - валидация ссылается на существующие датасеты/поля.

3. Сгенерируй скрипт нормализации на моём стеке (см. PROJECT_BRIEF.md).
   По умолчанию — Python + pandas (для Excel/CSV) или Node + xlsx (если я в
   чистом Node). Положи скрипт в scripts/build-dashboard-json.{py|js}.
   Скрипт должен:
     - читать source-manifest.yaml и metric-catalog.yaml;
     - загружать все источники;
     - применять mapping и transforms;
     - считать kpis по формулам из каталога;
     - заполнять charts и tables по series/датасетам;
     - писать data/dashboard.json.

4. Запусти скрипт и покажи мне сводку: сколько строк в каждом датасете, какие
   KPI посчитаны, время генерации.

5. Провалидируй итог по dashboard.schema.json. Если есть ошибки — чини и
   повторяй до зелёного прогона.

6. Покажи 10 случайных строк из самого крупного датасета для ручной проверки.

7. ОБЯЗАТЕЛЬНЫЙ post-check синхронизации с UI. Шаг не считается выполненным, если
   хотя бы одна проверка ниже красная:

   7.1. Считай ui-layout.yaml и собери все bind-ссылки (НЕ widget.id —
        widget.id относится только к UI и с dashboard.json не сверяется):
        - charts.<key> из tabs[].charts[].bind;
        - tables.<key> из tabs[].tables[].bind;
        - любые kind: image пути (logo, wear-image и т.п.).
        Для каждой такой ссылки проверь, что соответствующий ключ реально
        присутствует в dashboard.json и не пустой. Сформируй отчёт
        «widget.id | bind | присутствует | не пустой».

   7.2. Для series с forecastable: true из metric-catalog.yaml обязательно
        сгенерируй ряды *_forecast в dashboard.json.charts со структурой:
          { month, actual, forecast, lower, upper }
        - actual заполнен для исторических точек (forecast/lower/upper = null);
        - forecast/lower/upper заполнены для будущих точек (actual = null);
        - длина forecast-хвоста >= horizon из каталога (default 3).
        Без этих рядов шаг 7 считается проваленным.

   7.3. Для всех kind: image из ui-layout.yaml и всех путей в
        dashboard.json (brand.logo, charts.*.image, assets.*) — проверь,
        что файл существует на диске. Если путь вида assets/...  и
        физически файл лежит в data/assets/... — исправь путь ИЛИ перенеси
        файл так, чтобы один и тот же относительный путь работал из браузера
        (обычно — статическая раздача из корня проекта). В отчёте укажи,
        что именно изменил.

   7.4. Если любой подпункт 7.1/7.2/7.3 провален — НЕ отдавай dashboard.json
        как готовый. Сообщи конкретный список расхождений и останови работу
        до их устранения.

8. Инвалидация кэша. В самом dashboard.json всегда проставляй свежее
   meta.generated_at (ISO 8601 с таймзоной) и увеличивай meta.version при
   любом изменении схемы. Это нужно, чтобы UI мог корректно отличить старый
   кэш от нового билда.

9. Кодировки и кириллица (обязательно, особенно на Windows):

   9.1. Вход. Автодетект кодировки для каждого источника:
        - csv/tsv/txt: попробовать в порядке `utf-8-sig`, `utf-8`, `cp1251`,
          `cp866`, `windows-1252`; зафиксировать реальную в логе;
        - excel: всегда читать через библиотеку (openpyxl/pandas/xlsx),
          не через csv; листы с кириллицей не требуют явной кодировки;
        - json/parquet: utf-8 обязателен;
        - БД: задать client_encoding = UTF8 (PostgreSQL) / SET NAMES utf8mb4
          (MySQL).
   9.2. Нормализация. Все строки после чтения приводить к Unicode (Python
        `str`, Node `string`) БЕЗ дополнительных `encode/decode`. В
        dashboard.json сохранять `ensure_ascii: false` (Python) или
        дефолтный вывод (Node) — кириллица должна оставаться читаемой.
   9.3. Кириллица в именах колонок Excel/CSV. Не «чистить» и не
        транслитерировать: сравнение с mapping.columns идёт по точному
        совпадению строки (пробелы и регистр значимы).
   9.4. Вывод. dashboard.json сохранять строго в UTF-8 без BOM. Скрипт
        сборки обязан явно задавать encoding="utf-8" при записи.
   9.5. Контроль. В отчёте сборки отдельной строкой выведи:
        «Кодировки источников: <источник1 = utf-8, источник2 = cp1251, …>».
        Если где-то не смогли определить кодировку — остановись и спроси
        пользователя, не гадай.

Запрещено:

- Придумывать значения колонок и формулы сверх того, что описано в YAML.
- Заполнять нулями отсутствующие данные (только null / пустая коллекция).
- Хранить секреты в скрипте/YAML (только через переменные окружения).
- Отдавать dashboard.json как «готовый», если post-check §7 не пройден.
- Тихо дописывать недостающие charts/tables из головы — только через
  metric-catalog.yaml + source-manifest.yaml.

В конце сообщи: готов ли dashboard.json, что из validation прошло, что — нет,
и приложи итог §7 (матрица bind -> статус, список прогнозных рядов, список
путей к картинкам). Если всё ок — предложи отправить следующий промт:
kit/prompts/30-build-ui.md.
```
