# 30 — Сборка интерфейса дашборда

Отправьте, когда `dashboard.json` собран и в корне проекта лежат
`brand.config.yaml`, `ui-layout.yaml`, `metric-catalog.yaml`.

---

```
Режим: dashboard-builder. Действуй по kit/skills/dashboard-builder/SKILL.md и
kit/playbook/04-ui-spec.md.

Цель: сгенерировать работающий дашборд по трём конфигам + dashboard.json.

Шаги:

1. Подтверди со мной стек (если ещё не подтверждён):
   - Rendering: Vanilla HTML+JS / React / Vue / Svelte / Streamlit / Dash.
   - Chart library: ApexCharts / Chart.js / ECharts / Plotly / Recharts / Vega-Lite.
   - CSS: Vanilla / Tailwind / CSS-in-JS.
   Дефолт: Vanilla HTML+JS + ApexCharts + Vanilla CSS.

2. Создай каркас проекта:
   - index.html (или App под выбранный фреймворк);
   - css/styles.css с CSS-переменными из brand.config.yaml -> palette/typography;
   - js/app.js (или компоненты) с загрузкой data/dashboard.json.

3. Сгенерируй UI строго по ui-layout.yaml:
   - шапка (логотип + заголовок из brand.config);
   - чипы header.chips;
   - фильтры filters;
   - KPI-блок с карточками по kpi_block.cards (responsive-колонки);
   - вкладки tabs с charts/tables;
   - пустые состояния empty_state.text.

4. Применяй правила:
   - chart_policy.mono_by_default: один цвет, если легенда не несёт смысла;
   - categorical-палитра — для donut/pie/stacked-bar/multi-series;
   - KPI-подсветка по thresholds из metric-catalog.yaml;
   - формат чисел по i18n.locale, валюта по i18n.currency.

5. Обязательные UI-инварианты (не отмечай шаг как готовый, если нарушены):

   5.1. Загрузка данных. dashboard.json и любые сопутствующие JSON грузить
        строго с `fetch(url, { cache: "no-store" })` (или аналог для
        выбранного стека/фреймворка). Никогда не использовать агрессивный
        кэш — правки дашборда должны быть видны без ручной очистки.

   5.2. Прогнозный формат графиков. Если серия имеет поля
        actual/forecast/lower/upper (или помечена supports:
        [actual, forecast, confidence_interval]) — рендери её как
        multi-series график:
          - «Факт»: actual, сплошная линия, primary-цвет;
          - «Прогноз»: forecast, пунктир, accent-цвет;
          - «Доверительный интервал»: область между lower и upper
            (либо две пунктирные линии, если area-режим недоступен).
        Запрещено сводить такие данные к одной серии {x, y} и терять
        прогнозную семантику.

   5.3. Мягкое применение фильтров (формализация):

        Шаг 1. Построить compatibility map при загрузке дашборда:
          filterCompat[filterId][datasetId] = {
            hasField:  <true/false>,        // поле фильтра есть в датасете
            values:    Set<string>,          // уникальные значения поля в данных
          }

        Шаг 2. Правило применения конкретного фильтра filterId = value
        к конкретному виджету (chart/table/kpi), чей источник — datasetId:
          - если filterCompat[filterId][datasetId].hasField = false
              -> фильтр НЕ применяется, виджет рендерится на общем срезе;
              -> в dev-режиме логируем skip и причину "field missing";
          - если hasField = true, но value не в values И value != "all"
              -> фильтр НЕ применяется, виджет рендерится на общем срезе;
              -> в dev-режиме логируем skip и причину "value absent";
          - иначе -> фильтр применяется обычным способом.

        Шаг 3. Комбинация нескольких фильтров: правило применяется к
        каждому фильтру независимо; виджет может быть отфильтрован по
        одним фильтрам и проигнорировать другие (несовместимые).

        Шаг 4. Запрещено приводить всю вкладку к пустому состоянию
        из-за одного несовместимого фильтра. Если после применения всех
        совместимых фильтров датасет пуст — показываем
        `empty_state.text`, НЕ кидаем исключение и НЕ скрываем карточку.

        Шаг 5. Опционально: помечать виджеты, проигнорировавшие фильтр,
        небольшим бейджем «не затронут фильтром <label>», если это
        включено в brand.config.yaml -> ui.show_filter_skip_badges.

   5.4. Fallback путей для изображений. Для всех kind: image и любых img
        с относительным путём реализуй двухшаговый fallback:
          - сначала пробуем путь как указано в конфиге/данных;
          - при ошибке загрузки пробуем альтернативу: assets/... ↔
            data/assets/... (в обе стороны);
          - если оба варианта недоступны — показываем безопасный
            placeholder и пишем предупреждение в консоль (не 404-error).
        Наличие битой картинки считается регрессией.

   5.5. Валидация bind. Перед рендером каждой вкладки проходим по
        ui-layout.yaml -> tabs[].charts[].bind и tables[].bind. Для каждого
        bind проверяем наличие ключа в dashboard.json:
          - если ключа нет — рендерим `empty_state.text`, НЕ бросаем
            исключение и НЕ скрываем карточку;
          - в dev-режиме дополнительно логируем список отсутствующих
            биндов.

6. Проверь адаптив: 360 / 390 / 768 / 1024 / 1366 / 1920.
   Нет горизонтального скролла у страницы. Таблицы скроллятся в .table-wrap.
   Графики перерисовываются на resize.

7. Запусти локальный сервер (http-server / vite preview / уместный для стека)
   и сообщи URL.

8. Пройди автоматически проверяемые пункты
   kit/templates/acceptance-checklist.md §§ 2, 3, 4, 5, 6, 7, плюс новый §11
   (smoke-проверки UI).

Запрещено:

- Хардкодить метрики, подписи, цвета — всё должно читаться из конфигов.
- Писать бизнес-логику в UI-коде. Формулы — только в metric-catalog.yaml.
- Добавлять тексты на английском, если i18n.locale != en-*.
- Оставлять в UI технические идентификаторы (kpis.*, charts.* и т.п.).
- Кэшировать dashboard.json (в том числе Service Worker'ом) без явного
  инвалидатора по meta.version.
- «Обнулять» вкладки при неподдерживаемом значении фильтра.

В конце сообщи: что сделано, какие пункты чек-листа закрыты, какие — требуют
ручной проверки. Явно отчитайся по 5.1–5.5 и по smoke-тестам UI §11.
Предложи следующий промт: kit/prompts/40-setup-agent.md (если включен
AI-ассистент) или kit/prompts/90-acceptance.md.
```
