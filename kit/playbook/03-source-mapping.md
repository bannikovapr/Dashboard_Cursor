# 03. Source Mapping — подключаем источники

## Цель

Описать, откуда берутся данные, как их колонки называются в ваших файлах и в
какие «каноничные» датасеты они превращаются. Всё это — в одном файле
`source-manifest.yaml`.

Образец — [templates/source-manifest.example.yaml](../templates/source-manifest.example.yaml).

## Поддерживаемые источники

- `excel` (.xlsx, .xls) — несколько листов в одном файле допустимы.
- `csv`, `tsv` — с явным разделителем и кодировкой.
- `json`, `parquet` — прямое чтение.
- `sqlite` — файл + путь к таблице.
- `postgres`, `mysql` — DSN через переменную окружения.
- `api` — HTTP с bearer/basic-аутентификацией, JSON-ответы.
- `gsheet` — Google Sheets (потребуется service account).

## Алгоритм заполнения

1. **Перечислите источники.** Для каждого — `id`, `kind`, путь/DSN/URL.
2. **Объявите каноничные датасеты** в секции `canonical_datasets` — что в итоге
  должно попасть в `dashboard.json -> datasets`.
3. **Для каждого источника опишите mapping** — какие колонки источника
  соответствуют полям каноничного датасета.
4. **При необходимости добавьте `transforms`** — нормализация регистров,
  приведение типов, парсинг дат.
5. **Настройте `validation`** — что обязательно должно быть на выходе.

## Пример на минимальном кейсе

```yaml
sources:
  - id: orders_xlsx
    kind: excel
    path: "data/orders_2025.xlsx"
    sheet: "orders"
    mapping:
      - to: orders
        columns:
          order_id:  "Номер заказа"
          customer_id: "ID клиента"
          channel:   "Канал"
          amount:    "Сумма"
          created_at: "Дата"

canonical_datasets:
  - id: orders
    fields: [order_id, customer_id, channel, amount, created_at]

validation:
  required_datasets: [orders]
  required_fields:
    orders: [order_id, amount, created_at]
```

## Правила

- Имена исходных колонок пишите ТОЧНО, как в файле. Пробелы, регистр, символы —
значимы.
- Если один источник даёт несколько каноничных датасетов — повторяйте блоки
`mapping.to` внутри одного источника.
- Если нескольких источников недостаточно для одного датасета, агент умеет
собирать union. Главное — чтобы поля совпадали по именам и типам.
- Секреты (пароли, токены) — только через `dsn_env`/`token_env` и переменные
окружения. Никогда не пишите их в YAML.

## Генерация скрипта

После того как `source-manifest.yaml` готов, отправьте агенту промт
[prompts/20-map-data.md](../prompts/20-map-data.md). Агент:

1. Проверит манифест на корректность.
2. Сгенерирует скрипт нормализации на вашем стеке (Python или Node по умолчанию).
3. Запустит его и создаст `dashboard.json`.
4. Провалидирует результат по схеме `dashboard.schema.json`.

Агент действует по `skills/data-mapper/SKILL.md` — он не придумывает поля и
возвращает явную ошибку, если маппинга не хватает.

## Критерий готовности

- `source-manifest.yaml` заполнен и пройдена валидация агентом.
- Файл `dashboard.json` существует в проекте и не пустой.
- В консоли/логе агент отчитался: сколько строк в каждом датасете.
- Открыв `dashboard.json`, вы видите разумные числа в `kpis` — они совпадают
с вашей интуицией по источникам.

## Частые ошибки

- **«Не могу найти колонку»** — агент честно сообщит, какой колонки нет.
Исправьте имя в `mapping.columns` и запустите ещё раз.
- **«Даты в будущем»** — проверьте формат дат и часовой пояс (`defaults.tz`).
- **«KPI = 0, хотя данные есть»** — обычно причина в `transforms`: строки не
приведены к числам. Добавьте `to_number: true`.
