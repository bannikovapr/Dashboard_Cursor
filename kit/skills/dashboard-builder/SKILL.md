# Dashboard Builder — универсальный регламент

## Роль

Ты senior frontend-инженер. Твоя задача — собрать готовый дашборд на СТЕКЕ,
который выбрал пользователь, используя ЧЕТЫРЕ входа:

1. `dashboard.json` — данные (контракт `templates/dashboard.schema.json`).
2. `ui-layout.yaml` — карта интерфейса (KPI, вкладки, графики, таблицы).
3. `brand.config.yaml` — логотип, цвета, шрифты, локаль, адаптив.
4. `metric-catalog.yaml` — формулы, пороги, единицы, форматы.

Ни один из этих файлов не связан с конкретным доменом. Ты не привязан ни к
ТОиР, ни к продажам, ни к HR — ты строишь UI из конфига.

## Выбор стека

Перед генерацией подтверди со пользователем:

- **Rendering**: статический фронт (Vanilla HTML+JS), SPA (React/Vue/Svelte),
  server-rendered (Next/Nuxt), Python-native (Streamlit/Dash/Panel).
- **Chart library**: ApexCharts, Chart.js, ECharts, Plotly, Recharts, Vega-Lite.
- **CSS**: Vanilla CSS, Tailwind, CSS-in-JS, styled-components.
- **Бэкенд для ассистента**: нужен (Node/Python/Go/Rust) или нет.

Если пользователь не знает — предложи дефолт: **Vanilla JS + ApexCharts + Vanilla CSS**
(быстро, без сборщика, работает где угодно).

## Инварианты (один стек не важен — соблюдается всегда)

### 1) Controls system

Все элементы управления (селекты, кнопки, табы, поля, чипы) выглядят как ОДНА
система: одинаковые радиусы, толщина бордера, `hover/focus/active`.

- Кнопки: база = бренд-акцент в окантовке на белом, hover/active = заливка акцентом + белый текст.
- Поля ввода/контейнеры: нейтральная рамка `palette.border`, без случайного цвета.

### 2) KPI-карточки

- Количество и порядок — строго по `ui-layout.yaml -> kpi_block.cards`.
- Колонок: `columns_desktop / columns_tablet / columns_mobile` из конфига.
- Цвет значения: класс `kpi-status-target | standard | below | none` по формулам
  порогов из `metric-catalog.yaml`. При `null/NaN` статус не ставим.
- Формат значения: `metric-catalog.yaml -> kpis[].format` (`number | currency | percent | duration`, `compact`, `decimals`).

### 3) Политика цветов графиков

- По умолчанию моно-цвет `palette.chart.bar` / `palette.chart.line`.
- Categorical-палитра (`palette.chart.categorical`) — ТОЛЬКО если легенда несёт
  смысл: donut, pie, stacked-bar, multi-series.
- Никакой "радуги" ради декора.

### 4) Адаптивность

Проверка на брейкпоинтах из `brand.config.yaml -> breakpoints`.

- Нет горизонтального скролла у страницы.
- Таблицы скроллятся внутри `.table-wrap`.
- Графики пересчитываются на ресайзе (для ApexCharts — `redrawOnParentResize: true`).
- KPI-сетка: mobile = 1 колонка, tablet = 2, desktop/wide = из конфига.

### 5) Рендер графиков

- Для каждого графика биндинг из `ui-layout.yaml -> tabs[].charts[].bind`.
- Если `bind` указывает на отсутствующий или пустой ключ `dashboard.json` —
  показать пустое состояние (`empty_state.text`), НЕ бросать ошибку в консоль.
- Прогнозные графики (серии с полями `actual/forecast/lower/upper` или
  `supports: [actual, forecast, confidence_interval]`) ВСЕГДА рендерятся
  как multi-series:
  - «Факт» — сплошная линия по `actual`;
  - «Прогноз» — пунктир по `forecast`;
  - «Доверительный интервал» — область между `lower` и `upper`
    (или две пунктирные линии, если area недоступна).
  Запрещено сводить такие серии к одной линии `{x, y}` — это ломает
  семантику и скрывает прогноз.

### 7) Загрузка данных и кэш

- `dashboard.json` (и любые сопутствующие JSON) грузим строго с
  `fetch(url, { cache: "no-store" })` или эквивалентом для стека.
- Никаких Service Worker'ов / агрессивных CDN-заголовков без явного
  инвалидатора по `meta.version`.
- Изменение `dashboard.json` на диске должно быть видно после обычного
  reload без чистки кэша вручную.

### 8) Фильтры — мягкое применение (формальный контракт)

1. При загрузке UI строится `filterCompat`:

   ```
   filterCompat[filterId][datasetId] = {
     hasField:  boolean,      // поле фильтра есть в датасете
     values:    Set<string>   // уникальные значения поля в этом датасете
   }
   ```

2. Для конкретного виджета с источником `datasetId` при активном
   фильтре `filterId = value` действует правило:

   - `hasField == false` → фильтр НЕ применяется (skip, reason
     `field_missing`); виджет рендерится на общем срезе.
   - `hasField == true && value != "all" && !values.has(value)` →
     фильтр НЕ применяется (skip, reason `value_absent`); виджет
     рендерится на общем срезе.
   - Иначе → фильтр применяется обычным способом.

3. Несколько активных фильтров применяются независимо друг от друга —
   тот же виджет может быть отфильтрован по одним и проигнорировать
   другие.

4. После применения совместимых фильтров датасет может оказаться пуст —
   показываем `empty_state.text` из `ui-layout.yaml`. НЕ кидаем
   исключение, НЕ скрываем карточку.

5. Запрещено обнулять всю вкладку одним несовместимым фильтром —
   хотя бы один виджет должен остаться видимым (на общем срезе), если
   данные в принципе есть.

6. В dev-сборке логировать каждое skip-событие форматом
   `filter:<filterId> dataset:<datasetId> reason:<field_missing|value_absent>`.
   Это диагностика для data-mapper'а.

7. Опционально: бейдж «не затронут фильтром <label>» над виджетами,
   которые скипнули фильтр. Управляется флагом
   `brand.config.yaml -> ui.show_filter_skip_badges` (по умолчанию false).

### 9) Изображения и статические ассеты

Контракт путей:

- Канонический корень — `brand.config.yaml -> paths.assets_root` (по
  умолчанию `assets/`). Все пути в UI и в `dashboard.json` — относительные
  от этого корня.
- Разрешены: относительные пути (`assets/...`), `data:` URI для мелких
  иконок, абсолютные HTTPS URL для внешних ассетов.
- Запрещены: абсолютные ФС-пути, `..`-выходы за корень раздачи, дубли
  одного файла в разных путях.

Резолвинг в UI:

1. Сначала пробуем путь как есть из конфига/данных.
2. Если 404 — пробуем fallback `assets/...` ↔ `data/assets/...` (оба
   направления) строго ОДИН раз. Это страховка от исторических
   рассинхронов; в норме fallback не должен срабатывать.
3. Если и fallback не сработал — показываем безопасный placeholder и
   пишем предупреждение в консоль (не 404-error event).
4. Срабатывание fallback считается «жёлтой» регрессией: логируем в dev
   и добавляем в список к починке data-mapper'а (там должно быть
   приведено к каноничному пути).
- Битая картинка (оба варианта не сработали) — красная регрессия, FAIL.

### 6) Тексты и i18n

- Все подписи берём из конфига и `metric-catalog.glossary`.
- Никаких технических ключей JSON в подписях (`kpis.*`, `charts.*`, имена файлов).
- Локаль чисел и дат — `brand.config.yaml -> i18n.locale`.

## Процесс

1. Прочитать все 4 входных файла. Если `dashboard.json` ещё не собран —
   направить пользователя к `skills/data-mapper`.
2. Сгенерировать каркас приложения под выбранный стек.
3. Сгенерировать KPI-блок, вкладки, графики, таблицы, фильтры — всё из конфига.
4. Сгенерировать CSS-переменные из `brand.config.yaml -> palette/typography`.
5. Проверить пустые состояния, resize, переключение вкладок.
6. Пройти `kit/templates/acceptance-checklist.md` по пунктам 2–7.
7. При несоответствии — чини в месте конфига, а не в коде. Код должен
   оставаться "тупым" рендером конфига.

## Запрещено

- Хардкодить метрики, подписи, цвета — всё должно читаться из конфигов.
- Ломать контракт `dashboard.schema.json`. Если данных не хватает, расширяем
  контракт (согласовав с `data-mapper`), а не пишем в код "если есть — рисуй".
- Добавлять рекламные элементы и технические надписи.

## Definition of Done

- Дашборд открывается на всех 6 брейкпоинтах без горизонтального скролла.
- Все вкладки и все элементы из `ui-layout.yaml` отрисованы.
- `acceptance-checklist.md` пп. 2, 3, 4, 5, 6, 7 и §11 (smoke UI) — закрыты.
- `dashboard.json` грузится без кэша (`cache: "no-store"` или эквивалент).
- Прогнозные графики визуально отделяют факт / прогноз / интервал.
- Фильтры не обнуляют вкладки: несовместимые блоки остаются на общем срезе.
- Все изображения грузятся (нет `naturalWidth === 0`); fallback путей
  работает в обе стороны `assets/...` ↔ `data/assets/...`.
- Замена одного значения в `brand.config.yaml` меняет UI без правки кода.
- Замена `metric-catalog.yaml` меняет KPI и пороги без правки кода.
