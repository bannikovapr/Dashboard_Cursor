# Acceptance-чек-лист дашборда

Скопируйте этот файл в свой репозиторий и проходите по пунктам после того,
как агент собрал дашборд. Это DoD (Definition of Done) — если хотя бы один
блок не выполнен, просите агента доработать через `kit/prompts/99-fix.md`.

## 1. Данные

- Файл `dashboard.json` существует и валиден по `kit/templates/dashboard.schema.json`.
- В `meta.generated_at` стоит свежая дата.
- Все датасеты из `source-manifest.yaml -> validation.required_datasets` присутствуют и непусты.
- Числа, которые я могу проверить руками по источнику, совпадают с KPI на экране.
- Отсутствующие данные отображаются как `—` или `Нет данных`, а НЕ как `0`.

## 2. KPI-блок

- Все KPI из `metric-catalog.yaml -> kpis` показаны как карточки.
- Порядок карточек совпадает с `ui-layout.yaml -> kpi_block.cards`.
- У каждой карточки корректная единица и формат (валюта/процент/число).
- Цветовая подсветка статуса (зелёный/жёлтый/красный) соответствует порогам из каталога.
- При `null`/`NaN` цветовой класс не применяется.

## 3. Графики

- Все графики из `ui-layout.yaml -> tabs[].charts` отрисованы.
- Если серия одна и легенда не несёт смысла — цвет одноцветный (см. `chart_policy.mono_by_default`).
- Если есть осмысленные категории (структура, доли) — используется categorical-палитра.
- После переключения вкладок графики не ломаются и перерисовываются без артефактов.
- Пустой график показывает текст пустого состояния, не выбрасывает ошибку в консоль.

## 4. Таблицы

- Все таблицы из `ui-layout.yaml -> tabs[].tables` отрисованы.
- Заголовки колонок и форматы значений соответствуют конфигу.
- Горизонтальный скролл только внутри `.table-wrap`, а не у страницы.

## 5. Фильтры

- Все фильтры из `ui-layout.yaml -> filters` присутствуют.
- Изменение фильтра обновляет KPI, графики и таблицы.
- Опции, помеченные `options_from`, берутся из данных, не из хардкода.
- Чипы в шапке (`header.chips`) показывают актуальный контекст среза.

## 6. Бренд и локализация

- Логотип, заголовок, цвета, шрифты соответствуют `brand.config.yaml`.
- Числа и даты отформатированы по локали `i18n.locale`.
- Валюта отображается согласно `i18n.currency`.
- Все тексты интерфейса — на целевом языке (`i18n.locale`), без машинного английского.

## 7. Адаптивность

Проверить на ширинах: 360 / 390 / 768 / 1024 / 1366 / 1920.

- Нет горизонтального скролла у всей страницы.
- KPI складываются в 1/2/4 колонки по брейкпоинтам.
- Табы не ломают сетку; при нехватке места — скролл внутри зоны табов.
- AI-панель не занимает всю высоту экрана на мобильных без необходимости.

## 8. AI-ассистент (если включён)

- Ассистент отвечает строго по данным дашборда; не выдумывает цифры.
- Формат ответа соответствует выбранному (по умолчанию: факт → вывод → действие).
- Если облачная модель недоступна — работает локальный fallback.
- Ассистент не упоминает технические пути (`kpis.*`, `charts.*`, имена файлов).
- Язык ответов = `brand.config.yaml -> assistant.response_language`.

## 9. Прогноз (если включён)

- Для рядов, помеченных `forecastable: true`, работает запрос "Спрогнозируй на N периодов".
- В графике прогноза визуально отделены факт / прогноз / доверительный интервал.
- При недоступности прогнозного движка — понятный fallback, без 500-ошибок.

## 10. Безопасность и чистота

- `.gitignore` содержит `.env`, `.env.*` (с исключением `!.env.example`), кэш-папки и логи.
- `git check-ignore -v .env` возвращает путь `.env` (файл реально игнорируется).
- `git status` не показывает `.env` ни в staged, ни в untracked-to-commit.
- В репозитории нет `.env`, `*.pem`, `credentials.json`, `service-account.json` и им подобных.
- В исходниках скриптов/конфигов нет подстрок `sk-…`, `Bearer …`, реальных `*_API_KEY=…` — только ссылки на переменные окружения.
- Есть `.env.example` с плейсхолдерами (без реальных значений).
- Секреты для БД и API переданы через `dsn_env` / `token_env`, а не жёстко в YAML.
- В пользовательском UI нет технических идентификаторов и путей к файлам.
- Консоль браузера при обычной навигации чистая (без ошибок).

## 11. Smoke-тесты UI и данных

- Сверка ведётся по `bind`, а не по `widget.id`. Для каждого виджета из `ui-layout.yaml -> tabs[].charts[].bind` / `tables[].bind` соответствующий ключ в `dashboard.json.charts` / `dashboard.json.tables` существует и не пуст. Виджет с `widget.id` без `bind` или с `bind`, не резолвящимся в JSON, — регрессия.
- Для каждой series с `forecastable: true` в `dashboard.json.charts` есть ряд `*_forecast` с полями `{ month, actual, forecast, lower, upper }`, и прогнозная вкладка отрисовывает все ожидаемые графики (нет пустых карточек).
- Прогнозный график визуально содержит факт, прогноз и доверительный интервал (не «плоская одноцветная линия»).
- Все `kind: image` и все пути к изображениям в `dashboard.json` существуют на диске; `img.naturalWidth > 0` у ключевых картинок (логотип, износ и т.п.).
- Пути к изображениям соответствуют `brand.config.yaml -> paths.assets_root` (нет абсолютных ФС-путей, нет `..`-выходов, нет дубликатов одного файла в разных путях).
- `dashboard.json` грузится с `cache: "no-store"` (или эквивалент для стека): правка JSON видна без ручной очистки кэша.
- При смене любого фильтра (период / объект / класс) НЕ исчезают одновременно все графики и таблицы вкладки — несовместимые с фильтром датасеты остаются на общем срезе (`filterCompat` работает).
- В dev-консоли при смене фильтра видны skip-логи формата `filter:<id> dataset:<id> reason:<field_missing|value_absent>` (если таких случаев нет — логов просто нет; это нормально).
- Переключение вкладок и фильтров не даёт ошибок в консоли браузера.

## 12. Агент (если включён) — детерминированный роутинг

- 10 раз подряд POST `/api/agent` с вопросом «Покажи топ-5 … графиком» — во всех 10 ответах есть `artifacts` и `trace.toolsUsed` содержит `build_chart`.
- В chart ровно N категорий, где N — извлечено из запроса (или меньше, если данных физически меньше). `top_n` уважается без ручного подталкивания.
- Для «Спрогнозируй … на 3 месяца» ответ содержит artifacts и `trace.toolsUsed` = `forecast_metric`.
- В трассе каждого ответа видны intent-метки (intent, visualize_required, top_n, forecast_horizon) — маршрутизация делается детерминированно, а не «на удачу LLM».

## 13. Кодировки и кириллица

- `dashboard.json` открывается как UTF-8 без BOM; кириллица видна «как есть» (не `\uXXXX`).
- В логе сборки отдельная строка «Кодировки источников: …» со списком определённых кодировок по каждому источнику.
- Кириллические имена колонок из Excel/CSV корректно маппятся — значения попадают в KPI и графики без «?»-символов.
- Подписи в UI (легенды, тикеры, заголовки) показывают кириллицу корректно на русском и на заданной локали.

## 14. Security pipeline (если security-policy.yaml включён)

- В корне есть `security-policy.yaml`, версия и режим (`mode`) явно зафиксированы.
- На `GET /health` присутствуют поля: `mlReady`, `hardening.dlpKey`,
  `hardening.rateLimit`, `hardening.detector`. При `fail_mode=closed` и
  `mlReady=false` `/health` возвращает `503`.
- Запрос `POST /api/chat` с email и телефоном:
  * в `chat_model_request` (filter-trace) — только токены `[[DLP_*_NNNN]]`,
    raw email/phone отсутствуют;
  * в ответе фронту email/phone восстановлены через `restorePayload`.
- Запрос `POST /api/chat` с `sk-or-v1-…` (или другим секретом):
  * в `strict` — `400 dlp_blocked`;
  * в `monitor` — `200`, секрет токенизирован, в audit есть warn-event.
- При `DLP_ML_FAIL_MODE=closed` и недоступной ML-модели `/api/chat` и
  `/api/agent` возвращают `503 ml_unavailable`. Smoke-проверка
  (`smoke:failclosed-api`) проходит.
- Smoke-набор подключён к `ci:hygiene` и проходит:
  `smoke:agent-dlp`, `smoke:hardening`, `smoke:filter-trace`,
  `smoke:security-suite`, `smoke:failclosed-api`.
- Логи `logs/filter-trace.log`, `logs/dlp-agent-flow.log`,
  `logs/security-audit.log` — NDJSON, без сырых секретов; ротация работает
  (есть архивные файлы при превышении лимита).
- Rate-limit отсекает превышения (`429 rate_limited`); `chat` и `agent`
  имеют разные лимиты; `bypass_localhost` отключён в production.
- В репо нет `.env`, есть `.env.example` со всеми ключами из
  `security-policy.yaml -> env_keys` (без значений).

## 15. Windows-runtime (если запуск на Windows)

- PowerShell-обёртка запуска не падает на execution policy (внутри явно `Set-ExecutionPolicy -Scope Process` или используется `.cmd`).
- Перед стартом сервера скрипт проверяет/освобождает занятые порты (`netstat -ano` → `Stop-Process`), не «зависает на запуске».
- Логи сервера в PowerShell видны в UTF-8 (`chcp 65001`, `$OutputEncoding = UTF8`).
- Перезапуск после правок видит свежие файлы (старый `node`/`py` корректно завершается, нет «закешированного процесса»).
